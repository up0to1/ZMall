# ZMall AI 能力扩展 · 系统功能需求分析

## 一、背景与目标

### 1.1 业务背景

ZMall 当前已完成电商交易闭环（商品/购物车/订单/支付/优惠券/秒杀/社交流），具备向"智能化体验型电商"升级的基础。本次规划在现有微服务体系上扩展两大 AI 能力，**不重写底层，仅增量接入**。

### 1.2 战略目标

- **用户侧**：把"买衣服"从信息检索升级为"看效果决策"，降低决策成本
- **商家侧**：把"上新"从重资产拍摄降为轻算力生成，降低运营门槛
- **平台侧**：把"人找货"升级为"货找人"，构建数据护城河

### 1.3 数据假设与来源

| 数据 | 取值 | 来源 |
|------|------|------|
| 女装行业退货率 | 30%-50% | 艾瑞咨询《2024中国服饰电商退货率研究报告》、抖音电商公开数据 |
| 商家单次拍摄成本 | 千元级 | 项目对 3 家入驻商家访谈（待补充访谈记录） |
| 连带率基准 | 1.3 件/单 | ZMall 现有 trade-service 近 90 天数据（需 dashboard 拉取） |

> **行动项**：上述"商家访谈"和"dashboard 数据"需在 PRD 评审前补齐，否则指标目标值无依据。

## 三、AI 随心搭（用户端）

> **功能定位**：用户端的 AI 穿搭推荐 + 换装预览功能。整合了原"AI随心搭"（商品驱动）和"AI导购"（风格驱动）两种入口模式，统一为单一功能，降低用户认知成本和开发维护成本。商品驱动与风格驱动同属 **ai-outfit** 服务（端口 9001），不在 ai-models 服务。

### 3.1 两种入口模式

| 入口模式 | 触发场景 | 用户意图 | 智能程度 |
|---------|---------|---------|---------|
| **商品驱动** | 用户在商品详情页点击"AI随心搭"（绑定当前 itemId） | "我有这件上衣，帮我搭下装" | 直接向量检索互补商品 |
| **风格驱动** | 用户在独立页面选风格标签或输入场景描述 | "我要通勤风，帮我搭整套" | LangGraph Agent 编排选品 |

> **为什么整合？** 两种模式共享同一套核心能力（Qdrant检索 + 虚拟试衣换装 + 一键加购），只是输入入口和智能编排程度不同。拆成两个功能会导致用户认知混乱、开发重复、指标割裂。

### 3.1.1 LLM 模型选型（文本/视觉统一 qwen3.5-flash）

> **背景**：用户是否上传自拍照决定了 LLM 是否需要图像理解能力，以及 VTON 换装使用哪张 base 图。文本/视觉任务统一使用 `qwen3.5-flash`（全模态模型），不再按场景分流到不同 LLM 模型，仅 VTON base 图按是否上传自拍照区分。

| 场景 | 用户输入 | LLM 模型 | LLM 任务 | VTON base 图 | 适用用户故事 |
|---|---|---|---|---|---|
| **A** | 无自拍照 + 文本描述（风格/颜色/品类/场景/note） | `qwen3.5-flash`（全模态） | HyDE 改写 / note 解析 / 反馈解析 / 搭配决策 | 系统默认模特图（`default_model_image_url` 配置） | US-AT-03 |
| **B** | 有自拍照 + 文本描述 | `qwen3.5-flash`（全模态） | `analyze_user_photo`（提取性别/肤色/体型/年龄段/风格倾向/偏好色 6 个结构化字段）+ 同场景 A 的纯文本任务 | 用户自拍照（Redis `ai:photo:session:{userId}`） | US-AT-02 |

**模型选型理由**：
- **统一使用 qwen3.5-flash**：全模态模型，原生支持文本与视觉理解 + 函数调用，既能完成纯文本搭配决策，也能从用户自拍照中提取肤色/性别/风格倾向等结构化特征，供节点3 搭配决策时软性引导
- **搭配判定以结构化字段为主**：用户照片提取的 `user_visual_profile` 通过 `OUTFIT_SELECT_PROMPT` 第8条原则（用户视觉特征匹配）让 LLM 自然倾向匹配（性别硬过滤详见 §3.9）

> 详细实现见 `docs/AI核心功能设计.md` §3.12.1 模型选型与成本拆解、`docs/AI功能后端架构方案.md`。

**US-AT-08 Phase 2.5 实现方案补充（v3.2，2026-07-28）**：

> 原描述"基于购买历史推荐"过于宽泛，v3.2 明确 Phase 2.5 的实现方案：基于**浏览历史 + 购买历史 + 搭配 accept 历史 + 用户显式偏好**四类信号，聚合用户画像，用**加权 CLIP 向量融合 + 统计画像注入 LLM prompt** 双通道注入推荐链路。
>
> - **信号聚合**：浏览（`ITEM_VIEW`，权重 1.0）/ 加购（`CART_ADD`，权重 1.5）/ 下单（`ORDER_PLACE`，权重 2.0）/ 搭配满意（`OUTFIT_ACCEPT`，权重 3.0）/ dislike（`OUTFIT_DISLIKE`，权重 -2.0），按时间衰减（30 天全权重 / 30-90 天半衰减 / 90+ 丢弃）
> - **加权 CLIP 向量融合**：节点1 生成 `text_vector`（用户输入文本向量），与画像 `style_vector`（按信号权重加权的 CLIP 向量）融合，`final_vector = text_vector × (1-α) + style_vector × α`，`α = profile_confidence × 0.4`
> - **统计画像注入 LLM prompt**：将 `top_styles` / `top_colors` / `price_distribution` 注入节点3 `OUTFIT_SELECT_PROMPT`，引导 LLM 决策时参考用户历史偏好
> - **性别对齐**：画像聚合时按 `bodyProfile.gender` 硬约束过滤异性商品，异性商品仅提取颜色/价格/品类等中性属性
> - **浏览去噪**：停留 < 5s 丢弃、同商品浏览 ≥ 2 次才纳入、异性商品 × 0.1 权重需 ≥ 3 次
>
> 详见 `AI核心功能设计.md` §3.25 个性化推荐画像。

### 3.3 功能边界（MVP · v3 两阶段交互）

**输入**
- **商品驱动模式**：用户在商品详情页点击"AI随心搭"按钮（绑定当前 itemId）
- **风格驱动模式**（结构化表单 + 选填备注，**非聊天框式**）：
  - `styleTags`（可选，多选）：风格标签（通勤/休闲/约会/运动/商务/街头/复古/欧美/亚洲）
  - `color`（可选）：主色调筛选（red/black/white/blue/gray/khaki 等 Qdrant payload 精确匹配）
  - `categories`（可选，多选）：用户指定品类组合（上衣/下装/全身套装/鞋/帽子/包/配饰），不填则默认整套三件 `[上衣, 下装, 鞋]`
    · "全身套装" = 成套衣服/连衣裙/连体衣/旗袍等成套衣物，一件即覆盖全身（等价于上衣+下装，VTON 一次完成）
    · 半身裙归为"下装"，与上衣搭配走"上衣+下装"逻辑
    · 同时选"上衣+全身套装"时 VTON 顺序为先上衣后全身套装（全身套装覆盖上衣，符合"连衣裙套在上衣外"的搭配）
  - `shopId`（可选）：指定店铺内检索，不填则全平台
  - `sceneDesc`（可选，≤50字）：自然语言场景描述（如"下周面试"）
  - `note`（可选，≤50字）：自然语言备注补充，节点1 调用 LlmClient 解析后合并到上述结构化字段
  - `photoSessionKey`（可选）：用户真人照片会话 Key
  - **必填校验放宽**：`styleTags`/`color`/`sceneDesc`/`note` **任一非空即可**；全空时走默认季节风格 + 默认品类（US-AT-29）
- **照片输入**（两种模式通用，触发场景 A/B 路由）：可选上传用户真人照片（JPG/PNG，≤10MB，分辨率 ≥ 512×512）
  - **场景 A**（未上传照片）：系统使用 `system_model_image` 池中随机默认模特图兜底 VTON，LLM 走 `qwen3.5-flash` 全模态模型
  - **场景 B**（已上传照片）：使用用户自拍照 VTON，LLM 走 `qwen3.5-flash` 图像理解模型，提取 `user_visual_profile`（性别/肤色/体型/年龄段/风格倾向/偏好色）
- **用户上下文**（Phase 2.5 起）：登录用户的浏览/购买历史

**处理（v3 两阶段）**

> **整流程合并扣费**：风格驱动整流程（阶段一 + 阶段二 VTON 3 套）可合并为 **OUTFIT_DIRECT = 17 credits**（= 2 credits 阶段一 OUTFIT_RECOMMEND + 5 × 3 credits 阶段二 OUTFIT_VTON）一次性扣费。

**阶段一：候选单品推荐**（OUTFIT_RECOMMEND，2 credits）
1. **意图理解**：
   - 商品驱动模式：直接以当前商品为种子，提取风格/品类约束
   - 风格驱动模式：LangGraph Agent 节点1 解析用户输入
     · 结构化字段（styleTags/color/categories/shopId/sceneDesc）直接透传
     · note 备注调用 LlmClient.parse_note 解析，提取出风格/颜色/场景等合并到对应字段
     · 必填校验：styleTags/color/sceneDesc/note 任一非空即可；全空走默认季节风格
     · **场景 B 视觉特征提取**：若用户上传自拍照，调用 `LlmClient.analyze_user_photo`（qwen3.5-flash）提取 6 个结构化字段
     · **场景 A 标记**：用户未上传照片时设置 `use_default_model=True`，跳过视觉特征提取
2. **搭配候选生成**：通过 Qdrant 检索风格互补商品
   - shop_id 非空时限定店铺内检索；该店铺某品类检索为空时自动 fallback 全平台检索补全
   - color 非空时 Qdrant payload 精确过滤
   - categories 非空时按用户指定品类检索；为空则默认 `[上衣, 下装, 鞋]`
3. **LLM 审美决策**：Top10 候选笛卡尔积 → LLM select_top_outfits 选 Top3 + reason
4. **Reflection 自检**（P2）：颜色协调/风格一致/季节匹配检查
5. ⚠️ **不触发节点4 VTON 生成**（关键差异：v3 拆分为两阶段）

**阶段一输出**：Top3 候选搭配（卡片式展示，含单品缩略图+名+价格+店铺名+LLM reason）
**阶段一交互**：
- 用户选 1-3 套 → 进入阶段二
- 用户选"全部不满意，重新检索" → 触发新一轮阶段一（"换一套"计数+1）

**阶段二：VTON 生成**（OUTFIT_VTON，5 credits × N 套）
1. 加载 state 快照（含 Top3 候选 + 用户照片 + 默认模特图）
2. 仅对 selectedOutfitIndexes 中的套装执行节点4 链式 VTON
3. 多套 VTON 并行（受 Semaphore(2) 限流）
4. OSS 上传 + Redis 任务状态 + WS 推送

**阶段二输出**：每套 1 张 VTON 最终图 + 对应单品信息
**阶段二交互**（4 个按钮分支，US-AT-30）：
- [满意-加购整套] / [满意-下单整套] → 效果图入库 ai_outfit_record + 调购物车/订单接口
- [全部不满意，重新 VTON] → 同一 Top3 候选 + 换模特图重 VTON（无免费首轮机制，每轮扣 OUTFIT_VTON 5×N credits；商品驱动反馈轮同样按 OUTFIT_VTON 5 credits/轮）
- [全部不满意，回到阶段一重新检索] → 触发新一轮阶段一

**失败兜底**：生成失败时降级为"商品平铺组合图"+ 文案提示 + 回滚 credits

**输出**
- 阶段一：Top3 候选搭配清单（含名称、价格、店铺、LLM reason）
- 阶段二：VTON 效果图（分辨率 ≥ 768×1024；基于用户照片或系统模特图）
- 满意套装入库 ai_outfit_record（含单品信息+VTON URL）

**闭环**
- 阶段一满意 → 选定套装 → 阶段二 VTON → 加购/下单整套（复用现有 cart-service/trade-service）
- 阶段一不满意 → "换一套"重新检索（无首次免费，每次推荐扣 OUTFIT_RECOMMEND 2 credits）
- 阶段二满意 → 加购/下单整套 → 效果图入库
- 阶段二不满意 → 重新 VTON（无免费首轮机制，每轮扣 OUTFIT_VTON 5×N credits）/ 回到阶段一重新检索

**v6 扩展能力**（2026-07-27 新增，详见 docs/AI核心功能设计.md §3.17 / §3.18）：
- **子 Agent 决策**（场景 1/2，US-AT-49/50）：节点1 意图理解 + 节点3.6 搭配决策引入 ReAct 子 Agent，LLM 自主决定调用哪些工具（parse_note / rewrite_query_hyde / analyze_user_photo / get_weather_season / encode_query_vector / re_search / get_item_details / call_price_balance / call_trending_styles），不再走固定流程。配置开关 `enable_intent_sub_agent` / `enable_decision_sub_agent` 默认开启，关闭时回退原 v3 固定流程
- **外部工具拓展**（US-AT-50/51）：新增 4 个外部服务工具——price_service（价格平衡分析）/ inventory_service（实时库存查询，过滤缺货商品）/ fashion_trend_service（流行趋势参考，AnySearch 实现，原 trend_service 已弃用）/ weather_service（天气推导季节，uapis.cn，默认城市北京），封装在 `shared/external_services/`，默认开启（weather_tool_enabled=True）
- **尺码推荐**（US-AT-48/52/53）：用户加购/下单时按需调用 `POST /items/size-chart/recommend-by-item?itemId={itemId}` 基于身体信息推荐尺码；商家维护店铺尺码对照参考表（三级回退：商品专用 > 店铺通用 > 系统模板）

### 3.4 关键合规要点（必须前置）

| 风险 | 应对 |
|------|------|
| **用户真人照片上传（肖像权）** | 上传前必须用户明确勾选授权同意书；明确告知照片仅用于本次换装生成，不用于其他用途；禁止上传他人照片（需人脸核验或声明） |
| **用户照片存储与删除** | 用户上传的照片**仅本次会话使用，会话结束后自动删除**，不永久存储；用户可随时主动清除；存储期间加密 |
| **未成年人保护** | 照片上传入口对未满 16 岁用户隐藏（依据《未成年人网络保护条例》）；禁止上传未成年人照片 |
| **AI 生成图真实性** | 换装效果图需标注"AI 生成效果图"提示，避免用户误认为实拍，引发"买家秀与卖家秀"纠纷 |
| **搭配推荐公平性** | 搭配排序不得仅按商家付费排名，需以风格匹配度为主，避免误导用户 |
| **用户行为数据使用** | 浏览/购买历史用于推荐需在隐私政策中明示，提供"关闭个性化推荐"开关 |
| **虚拟分身数据（Phase 3）** | 用户主动授权建立持久虚拟分身，加密存储，支持随时撤回和删除 |
| **Agent 决策可解释性** | 用户可查看"为什么推荐这套"的理由（风格匹配度 + 场景契合度） |

### 3.5 实现阶段 Phase

| Phase | 目标 | 核心能力 | 退出条件 |
|-------|------|---------|---------|

### 3.6 关键定义

**"complementary 互补商品"的工程定义**：
- **品类互补**：上衣 ↔ 下装/全身套装 ↔ 鞋类 ↔ 配饰（基于 item.category 的规则表）
  · "全身套装"（成套衣服/连衣裙/连体衣/旗袍等）特殊：一件即覆盖全身，等价于上衣+下装，不再互补上衣/下装
  · 半身裙归为"下装"，与上衣互补
- **风格互补**：商品风格向量（CLIP 提取）余弦相似度 ∈ [0.4, 0.8]（太低不搭，太高重复）
- **颜色互补**：基于色彩理论（互补色/同类色）的简单规则匹配
- **店铺约束**：MVP 阶段仅在同店铺内检索（降低跨店交易复杂度）

### 3.6.1 历史记录策略（v3.1）

> **决策**：MVP 阶段不做完全聊天式（任务制 + 跨轮上下文累积），通过"用户偏好持久化 + 任务恢复 + 满意套装永久保留"弥补聊天式体验。

| 数据类型 | 保留策略 | 清理方式 |
|---------|---------|---------|
| AI 随心搭满意套装（`ai_outfit_record`） | **永久保留** | 用户主动删除 |
| AI 随心搭/模特图任务记录（`ai_task`） | **90 天** | 定时任务每日 0:00 清理 SUCCESS/FAILED 状态且 > 90 天的记录 |
| AI 模特图评分反馈（`ai_model_image_feedback`） | **永久保留** | 不清理（Agent 优化数据） |
| 入池模特图（`system_model_image`） | **永久保留** | 运营手动下架或创建者删除 |
| 用户照片会话（Redis） | **30min TTL** | 自动过期 |
| LangGraph state 快照（Redis） | **1h TTL**（与 TASK_STATUS_TTL/MQ 幂等 TTL 对齐，2026-07-20 修复） | 自动过期 |
| 用户偏好（`user_preference`，Phase 2.5） | **永久保留** | 用户主动重置 |

### 3.7 Non-goals（明确不做）

- 不做跨店搭配（Phase 2 再做，需改造 trade-service 拆单）
- 不做用户照片永久存储（仅本次会话使用，会话结束自动删除）
- 不做用户照片用于换装以外的其他用途（如训练、分享、广告）
- 不做 3D 试穿（技术成本过高，ROI 不成立）
- 不做穿搭社区/UGC（先验证工具价值，社区是后续增长动作）
- 不做男装/童装（MVP 聚焦女装，品类扩张需独立验证）
- 不做实时多轮对话（MVP 是"提交→出结果"，多轮对话是 P2）
- 不做语音输入（技术成本高，先验证文本交互）
- 不做跨品类导购（如"搭配家居"），MVP 聚焦服饰
- 不做 Agent 自主下单（用户必须确认加购，Agent 不替用户决策交易）
- ~~**不做衣服单品性别过滤**~~（v6 已实施，2026-07-27 修订）：原 Non-goal 已撤销。商家上架时强制标注 `target_gender` 字段（男/女/中性），节点2 Qdrant 硬过滤 `target_gender IN (user_gender, "unisex")`，避免跨性别推荐。详见 [§3.9 性别与服装搭配需求](#39-性别与服装搭配需求v6-新增2026-07-27) 与 `AI核心功能设计.md §3.19`。

### 3.8 异常与降级

| 异常场景 | 降级方案 |
|---------|---------|
| 换装生成服务超时（>15s） | 返回"平铺组合图" + 提示"换装图生成中，稍后查看" |
| 店铺内互补商品不足 3 件 | 提示"本店搭配资源不足"，引导用户切换"全平台搭配"（Phase 2） |
| 用户上传照片质量不达标（模糊/遮挡/非正面） | 提示"请上传清晰正面全身照"，或降级使用默认模特照片 |
| 用户上传照片疑似未成年人 | 拒绝处理，提示"暂不支持未成年人照片" |
| LangGraph Agent 推理超时（>30s） | 标记失败 + WebSocket 推送失败提示 + 配额回滚 |
| 单用户 1 小时内生成 ≥10 次 | 触发限流（网关 RateLimitFilter，Redis ZSET 滑动窗口，`ai:rate:user:{userId}`），提示"休息一下" |
| 场景 A 默认模特图加载失败（`default_model_image_url` 未配置/URL 不可达） | 多层降级链：(1) Java 侧 `GET /items/admin/ai-model/system-images/random-default` 随机选取系统模特图池；(2) Python 侧 `GenClient.generate_text_only_model_image`（千问 Wan 图生图 wan2.7-image）兜底；(3) 最终降级为空 bytes 触发 PIL 商品图堆叠（体验较差），告警通知运营补充默认模特图 |
| 场景 B 用户照片 LLM 分析失败（qwen3.5-flash 超时/异常） | 不阻塞主流程，`user_visual_profile=None`，搭配决策退化到结构化字段判定（场景 A 同等逻辑） |
| **子 Agent ReAct 超时/超过最大轮次**（v6 新增） | IntentAgent 走 `_fallback_intent_result`（拼 query_text + 不生成向量）；DecisionAgent 走 `_fallback_decision_result`（accept=true 保留原 Top3）；反馈轮 ReAct 失败走原 ToolExecutor 固定流程 |
| **单个 Tool 执行失败**（v6 新增） | Tool 返回 `{"error": "..."}`，不抛异常，LLM 决定重试或换其他 Tool；不阻塞主流程 |
| **price_service 失败**（v6 新增） | 纯本地实现几乎不会失败；失败时返回默认评分 0.5，LLM 忽略价格约束 |
| **inventory_service 失败（item-service 不可用）**（v6 新增） | 返回空 dict，调用方降级为"不过滤"（保留所有候选，LLM 决策时忽略库存字段） |
| **fashion_trend_service 失败**（v6 新增，原 trend_service 已弃用） | 返回空趋势 `{"trending_styles": [], "error": "..."}`，LLM 仅凭用户意图推理 |
| **weather_service 失败（uapis.cn 调用失败）**（v6 新增） | 按月份推断季节（北半球默认映射）；城市未知用默认城市北京兜底 |
| **尺码推荐接口失败**（v6 新增） | 前端提示"暂无法推荐尺码，请查看尺码表自行对照"；不阻塞加购/下单主流程 |
| **商品无对应尺码表（三级回退全空）**（v6 新增） | 前端提示"暂无尺码参考表，请联系商家"；引导用户查看商品详情页联系商家 |
| **商品 `target_gender` 为空（旧数据未标注）**（v6 新增） | 代码统一硬过滤 `target_gender IN (target_gender, "unisex")`，`target_gender` 为空按 `unisex` 处理（不排除）；待 `reconcile_mysql_qdrant --fix-inconsistent` 回填；LLM prompt 双保险排除跨性别候选 |
| **用户未登记身体档案**（v6 新增） | 前端禁止提交 AI 搭配请求，引导跳转衣橱页登记 |
| **系统模特性别与身体档案性别不一致**（v6 新增） | 前端校验拦截，提示用户重新选择模特或更新档案 |
| **user-service `/body-profile` 接口故障**（v6 新增） | 节点1 catch 异常，降级跳过身体档案来源，仍可用系统模特/自拍分析确定 gender |

### 3.9 性别与服装搭配需求（v6 新增，2026-07-27）

> **需求来源**：用户反馈"AI 全平台找搭配时，男用户被推荐女款连衣裙、女用户被推荐男款西装"的跨性别推荐问题。v6 通过商品 `target_gender` 字段 + 用户/模特性别档案 + Qdrant 硬过滤 + LLM 双保险解决。

#### 3.9.1 核心需求

1. **跨性别推荐零容忍**：男用户/男模特只推荐 `male` + `unisex` 服装；女用户/女模特只推荐 `female` + `unisex` 服装。
2. **中性款保留**：T 恤、卫衣、牛仔外套、运动鞋、帽子、包等中性款（`unisex`）男女用户都可被推荐，避免丢失合适候选。
3. **性别来源优先级**：系统模特 > 用户自拍 LLM 视觉分析 > 身体信息档案，三者任一可用即可触发过滤。
4. **善意提醒**：前端在 AI 随心搭入口和衣橱登记页明确提示"请确保信息填写正确"。
5. **档案必填**：未登记身体档案时禁止使用 AI 搭配，引导用户先登记。

#### 3.9.2 性别信息登记要求

**用户身体档案**（`hm-user.user_body_profile`）：
- `gender` 字段必填（`male` / `female`）
- 登记页面红色警示文案："⚠️ 请如实选择性别：男用户推荐男款+中性款，女用户推荐女款+中性款"
- 支持多档案（如给家人朋友登记），但默认档案优先使用

**系统模特图池**（`hm-item.system_model_image`）：
- 每张模特图必须标注 `gender`（`male` / `female`）
- 前端按性别分区展示，带 ♂ 蓝 / ♀ 粉 标签
- 用户选定后用于 VTON base 图和性别过滤

**商品库**（`hm-item.item`）：
- 商家上架时强制选择 `target_gender`（`male` / `female` / `unisex`）
- 未标注默认 `unisex`，代码硬过滤 `target_gender IN (target_gender, "unisex")`，并通过 `reconcile_mysql_qdrant --fix-inconsistent` 回填

#### 3.9.3 性别过滤实现方式

**硬过滤（节点2 Qdrant 检索）**：
```
Filter: payload.target_gender IN (user_gender, "unisex")
```
- 男用户 → 匹配 `target_gender IN ("male", "unisex")`
- 女用户 → 匹配 `target_gender IN ("female", "unisex")`
- 跨店 fallback 同样传递 `target_gender`，确保全平台补全也不跨性别

**软引导（节点3 LLM 搭配决策）**：
- `OUTFIT_SELECT_PROMPT` 第10条原则要求 LLM 排除跨性别候选
- 作为 Qdrant 硬过滤的双保险，防止 payload 缺失导致漏过滤

#### 3.9.4 前端交互要求

| 页面 | 要求 |
|------|------|
| `wardrobe.html`（衣橱页） | 身体信息档案区块，性别必填 + 红色警示文案；未登记时显示"无法使用 AI 搭配" |
| `outfit-agent.html`（风格驱动） | 顶部性别提醒横幅；身体档案状态卡；系统模特选择（带性别标签）；提交前校验档案必填 + 性别一致性 |
| `outfit-product.html`（商品驱动） | 同风格驱动，但身体档案非必填（主商品已选定，仅用于互补商品过滤）；系统模特性别优先 |
| 系统模特选择模态框 | 男/女模特分区展示；点击查看详情（身高、肤色、风格标签）；选定后高亮显示 |

#### 3.9.5 验收标准

| 验收项 | 验收标准 |
|--------|----------|
| 跨性别推荐阻断 | 男用户/男模特的推荐结果中不含 `target_gender=female` 的商品；女用户/女模特同理 |
| 中性款保留 | 男用户/女用户的推荐结果中可包含 `target_gender=unisex` 的商品 |
| 性别来源优先级 | 系统模特选定时，`gender_source=system_model`；仅有自拍时，`gender_source=user_photo`；仅有身体档案时，`gender_source=body_profile` |
| 未登记档案拦截 | 未登记身体档案时，提交 AI 搭配请求被前端拦截并引导跳转衣橱页 |
| 性别一致性校验 | 选定系统模特性别与身体档案性别不一致时，提交被前端拦截 |
| 向后兼容 | 旧数据 `target_gender` 为空时，Qdrant 过滤排除该商品并记录日志，不阻塞主流程 |
| 跨店 fallback 一致性 | 跨店补全的候选商品同样符合性别过滤规则 |
| LLM 双保险 | Qdrant payload 缺失 `target_gender` 字段时，LLM 仍能根据 prompt 排除跨性别候选 |

### 3.10 两种使用模式需求（2026-07-28 v3.2 新增）

> **需求来源**：v6 引入"系统模特模式"后，用户无需上传自拍照即可体验 AI 搭配，但原设计与"自拍照模式"的边界混在一起，下单决策缺乏明确依据。v3.2 明确拆分为两种使用模式，约定各自的能力边界与下单引导路径。
>
> **关联用户故事**：US-AT-61（零门槛体验）、US-AT-62（系统模特转自拍照）。

#### 3.10.1 模式A：系统模特模式（浏览体验 + 穿搭灵感）

| 需求项 | 说明 |
|-------|------|
| **定位** | 浏览体验 + 穿搭灵感（"看别人穿"） |
| **门槛** | 零门槛，无需登记 `bodyProfile`，无需上传真人照片 |
| **身体信息来源** | 系统模特档案（`system_model_image` 表的 `gender`/`height`/`weight`/`bodyType`/`ageRange`） |
| **性别确定** | 由用户选定的系统模特 `gender` 决定 |
| **支持能力** | 多轮反馈调整、保存到衣橱、加购商品（自选尺码，无尺码推荐） |
| **不支持能力** | ❌ 直接下单（效果图 ≠ 用户上身效果）、❌ 尺码推荐（无用户三围数据） |
| **下单引导** | 用户点"下单" → 引导上传真人照片 → 复用搭配 + 用户照片重新做 VTON（§3.10.3） |

#### 3.10.2 模式B：自拍照模式（真实试穿 + 放心下单）

| 需求项 | 说明 |
|-------|------|
| **定位** | 真实试穿 + 放心下单（"看自己穿"） |
| **前置条件** | 必须登记 `bodyProfile`（含完整三围） + 上传真人照片 |
| **身体信息来源** | 用户 `bodyProfile`（含 `bust`/`waist`/`hip`/`height`/`weight`/`gender`） |
| **性别确定** | 由 `bodyProfile.gender` 决定 |
| **支持能力** | 多轮反馈调整、保存到衣橱、加购商品、**直接下单 + 尺码推荐** |

#### 3.10.3 系统模特模式转自拍照模式

> **未实现（仅设计未实现）**：本节对应端点 `POST /v1/outfit/agent/re-vton-with-photo` 未实现，仅设计未实现。若后续落地，扣费按 OUTFIT_VTON 5×N credits（无 2 credits 档）。

**场景**：用户用系统模特模式看到喜欢的搭配，想看自己穿上效果后再决定下单。

**流程**：
1. 模式A 系统模特生成搭配（5 credits，已扣）
2. 用户对搭配满意 → 点击"下单"按钮
3. 前端检测当前为模式A → 弹出引导弹窗："想看自己穿上效果吗？上传照片可生成你的真实试穿图"
4. 用户上传真人照片 → 调 `/re-vton-with-photo` 接口
5. 后端复用原搭配（`itemId` 列表不变）+ 用户照片做 VTON，仅执行节点4 链式 VTON（不跑节点1/2/3）
6. 扣 OUTFIT_VTON（5 × N credits）→ 生成新效果图（用户本人上身）→ 转为模式B
7. 用户看到自己穿上效果 → 可直接下单（含尺码推荐）

**关键约束**：
- 复用搭配（`itemId` 列表不变，只换 VTON 底图）
- 仅 VTON（不跑节点1/2/3）
- 扣费按 OUTFIT_VTON（5 × N credits），无 2 credits 档
- 性别一致性校验：用户 `bodyProfile.gender` 必须与原系统模特 `gender` 一致

#### 3.10.4 核心原则

1. **效果图与尺码推荐基于同一身体数据源**：避免"看别人穿、按自己尺码下单"的数据源错配
2. **系统模特模式是"看别人穿"**：用户预览搭配灵感，效果图非用户上身效果
3. **自拍照模式是"看自己穿"**：用户看到真实上身效果，下单决策有可靠依据
4. **下单决策应基于"看自己穿"**：模式A 不允许直接下单，必须引导转模式B

> **关联设计文档**：[AI核心功能设计.md §3.20 两种使用模式](AI核心功能设计.md) / [§3.21 系统模特模式转自拍照模式](AI核心功能设计.md)。

### 3.11 浏览记录功能需求（2026-07-28 新增）

> **需求来源**：Phase 2.5 个性化推荐画像需要用户浏览历史作为弱正信号（`ITEM_VIEW`，权重 1.0），原需求未明确浏览记录的采集和管理机制。v3.2 补全浏览记录功能需求。

#### 3.11.1 浏览记录采集

| 需求项 | 说明 |
|-------|------|
| **触发时机** | 用户打开商品详情页时自动记录浏览（无需用户主动操作） |

| **去重规则** | 5 分钟内重复浏览同一商品仅记 1 次（更新 `viewed_at`，不新增记录） |
| **去噪规则** | 停留 < 5s 视为误点击，**不纳入画像聚合**（但仍记录在浏览历史表，供用户查看） |

| **单条删除** | 每条浏览记录右侧"删除"按钮，单条删除 |
| **批量删除** | 多选框 + "批量删除"按钮，支持批量删除选中记录 |
| **清空所有** | 顶部"清空所有"按钮，二次确认后清空该用户所有浏览记录 |
| **跳转商品** | 点击浏览记录卡片跳转到对应商品详情页 |
| **展示字段** | 商品图 / 商品名 / 价格 / 浏览时间 / 来源页标签 |

#### 3.11.3 浏览数据用途

| 用途 | 说明 |
|------|------|
| **AI 随心搭 Phase 2.5 个性化推荐画像** | 浏览历史作为 `ITEM_VIEW` 信号（权重 1.0）聚合到用户画像，用于风格向量融合和 LLM prompt 注入 |
| **去噪策略** | 停留 < 5s 丢弃 / 同商品浏览 ≥ 2 次才纳入 / 异性商品 × 0.1 权重需 ≥ 3 次（详见 `AI核心功能设计.md` §3.25.4） |

#### 3.11.4 隐私与合规

| 需求项 | 说明 |
|-------|------|
| **隐私政策明示** | 浏览历史用于推荐需在隐私政策中明示，提供"关闭个性化推荐"开关 |
| **用户可控** | 用户可随时查看/删除/清空浏览历史，删除后不影响其他功能 |

#### 3.11.6 数据表设计

**`user_browse_history` 表**（位于 `hm-user` 数据库）：

### 4.2 功能边界（MVP · v3 含评分发布流程）

**输入**
- 商品：1-4 件店铺自有商品（必须为穿搭类目：上衣 / 下装 / 全身套装 / 帽子 4 类）
  - 商品类目校验：`category ∈ AI_MODEL_SUPPORT_CATEGORIES = [上衣, 下装, 全身套装, 帽子]`
  - 商品归属校验：`item.creater == 当前 shopId`
  - 品类冲突校验（P0）：
    · 同品类最多 1 件（千问 aitryon-plus 单次只能穿 1 件同类商品）
    · 全身套装与上衣/下装互斥（全身套装已覆盖上下身，逻辑矛盾）
    · 全身套装与帽子可共存（套装→帽子 2 次生成）
    · 允许组合清单：[上衣]、[下装]、[全身套装]、[帽子]、[上衣+下装]、[上衣+帽子]、[下装+帽子]、[上衣+下装+帽子]、[全身套装+帽子]（共 9 种合法组合）
  - 商品图：JPG/PNG，≤5MB，分辨率 ≥ 512×512，白底图优先
- 模特图来源（v2 统一系统模特图池 · 二选一约束）：
  - **方式 A：商家上传新模特图**（POST /items/admin/ai-model/system-images，multipart）
    - 自动加店铺名水印（防滥用），存 OSS 优先 / 本地回退
    - 必填字段：性别/肤色/身高/体重/年龄段/体型/风格标签/备注
    - 入池后返回 modelImageId，调 generate 接口
  - **方式 B：从全平台共用的系统模特图池选一张**（GET /items/admin/ai-model/system-images）
    - 所有商家都能查 is_active=1 的图（含其他商家上传的）
    - 仅创建者（uploader_user_id）能修改/删除自己的图
    - 选定后拿 modelImageId 调 generate 接口
  - **必填约束**：`AiModelGenerateDTO.modelImageId` 必填，前端"二选一"流程保证

**处理**
1. **请求校验**（Java 侧）：商品数量 ∈ [1,4] + 类目清单匹配 + 商品归属 + 模特图来源解析 + credits 预扣（5 credits）
2. **MQ 异步入队**：taskId + 商品列表（按链式顺序） + 模特图 URL → `ai.model.generate` 队列
3. **链式 VTON 生成**（Python 侧）：
   - 链式顺序：全身套装（一次覆盖全身）→ 上衣 → 下装 → 帽子（全身套装优先，避免被覆盖）
   - 套装组合特例：[全身套装, 帽子] 仅 2 次生成
   - 三件组合：[上衣, 下装, 帽子] 3 次生成
   - 单件：[上衣] 1 次生成
   - 调 `VtonClient.try_on_chain_with_intermediates` 返回 `list[bytes]`
   - 单件失败不中断，用上一步结果继续；全部失败 → 降级 PIL 贴图合成
   - 重试策略：模型 API 瞬时失败重试 3 次（指数退避 2s/4s/8s）
4. **中间图收集**：每件单品穿上后的结果都收集，按链式顺序产出 N 张图（最后一张即最终合成图）
5. **OSS 上传**：文件名 `{taskId}_{step}_{category}.jpg`，获取 N 个 OSS URL
6. **结果回流**：MQ 通知 Java 更新 `ai_task` 表 + 确认/回滚 credits + WebSocket 推送商家

**输出**
- N 张中间图 + 1 张最终图（N = 商品件数；最后一张与最终图为同一张）
  - 单件上衣：1 张
  - 上衣+下装：2 张
  - 上衣+下装+帽子：3 张
  - 全身套装+帽子：2 张

**评分与发布流程**（v3 新增，详见 docs/AI核心功能设计.md §1.9）
1. 任务 SUCCESS → 前端展示 N 张图 + 弹出五星评分对话框
2. 商家评分（1-5 星 + 可选标签 + 备注）→ POST /items/admin/ai-model/tasks/{taskId}/rating
3. rating ≥ 3 ★：最终图自动入 system_model_image 池（source=1，复用）
4. rating ≤ 2 ★：仅记录评分，不入池
5. 评分后弹出"一键发布到商品详情页"对话框：[全部发布] [选择发布] [暂不发布]
6. 选 [全部发布] / [选择发布]：调 ItemService.updateItemMainImage + 同步 Qdrant 向量
7. 选 [暂不发布]：必填拒绝原因 → POST /items/admin/ai-model/tasks/{taskId}/reject-reason
8. rating ≤ 2 ★ + 拒绝发布：致歉 + 引导用户重新选品生成
- 分辨率 ≥ 768×1024，存入 OSS
- 每张图标注对应品类（前端展示用 `itemCategories` 数组）
- 预览页面 + 单张"重新生成"按钮（仅重做该步及后续步骤）
- 确认后一键发布到对应商品的主图位

**闭环**
- 满意 → 选定中间图或最终图 → 发布到对应 itemId 的商品主图位 → 清商品缓存
- 不满意 → 单步重新生成（仅重做该步及后续步骤，限制 5 次/任务，防滥用）
- 临时上传模特图勾选保存 → 写入统一 `system_model_image` 池（source=0=商家上传，归属当前 shopId；无 `shop_model_image` 表）

**v5 三种生成模式**（2026-07-26 新增，详见 docs/AI核心功能设计.md §1.10）：

| 模式 | 商品数 | 输出图数 | credits | 典型场景 |
|------|--------|---------|---------|---------|
| **single**（v3 原模式） | 1 件上装 + 1 件下装 / 1 件全身套装 | 1 张最终图（+N 张中间图） | 5 | 单品上新，1 张主图 |
| **multi_outfit**（多换装搭配） | 2-4 件商品（可同品类多件） | 1-4 张图（每套 1 张） | 18 | 一次拍多套搭配，商品页轮播图 |
| **multi_pose**（多姿势变体） | 1 件上装 + 1 件下装 / 1 件全身套装 | 1 张基准图 + N 张姿势变体（默认 3，最大 4） | 3 + 3 × poseCount | 单款多角度展示，详情页多图 |

**关键设计**：
- **同脸一致性**（US-AM-17）：multi_outfit 通过"共用同一张模特基准图"保证所有换装图脸部一致；multi_pose 通过"VTON 基准图为参考"保证所有姿势变体脸部、妆造、服装一致
- **部分失败不阻塞**（US-AM-18/19）：multi_outfit 单套 VTON 失败时其他套正常返回；multi_pose 图生图（aitryon-refiner / wan2.7-image）失败时降级复用 VTON 基准图
- **搭配组合推荐**：multi_outfit 模式下，Python LLM（`outfit_combination_subgraph.recommend_outfit_combinations`）基于商品风格/颜色/品类自动推荐 1-4 套合法搭配组合；LLM 不可用时降级走笛卡尔积（每件商品独立成套）
- **MQ 消息体扩展**：新增 `generationMode`（single/multi_outfit/multi_pose）+ `outfitCombinations`（可选）+ `poseCount` 字段，由 model_consumer 路由到对应工作流

### 4.3 关键合规要点（必须前置）

| 风险 | 应对 |
|------|------|
| **AI 生成图版权** | 选用商用授权的生成模型；用户协议明确"生成图版权归商家所有" |
| **模特肖像权（平台公共池）** | 仅使用平台预设的 AI 虚拟模特或商用授权模特图（非真人脸）；由平台法务统一签授权 |

| **商品还原度** | 生成图与实物色差超过阈值时，系统提示商家"请核对实物颜色" |

### 4.4 实现阶段 Phase

| Phase | 目标 | 核心能力 | 退出条件 |
|-------|------|---------|---------|
| **Phase 1（MVP）** | 多商品链式 VTON + 统一系统模特图池 | 1-4 件商品链式生成 + 统一 `system_model_image` 池（source 0=merchant/1=AI-saved/2=platform/3=AI-auto）+ 中间图输出 + 单张发布 | 商家生成图 ≥ 1000 张/日，商家使用率 ≥ 30% |

### 4.5 Non-goals

- 不做商家上传真人模特图的"换脸/换妆"等深度编辑（仅用于 VTON base 图，不做后期人脸修改）
- 不做视频模特生成（成本过高，MVP 不验证）
- 不做模特图后期编辑（裁剪/滤镜由商家用其他工具完成）
- 不承诺生成图可用于全平台投放（不同平台合规要求不同）
- AI 模特端**不支持**饰品/包类/鞋类的链式 VTON（与 AI 随心搭 7 类清单不同；商家端只做服装主体 + 帽子共 4 类）
- ~~**不做性别硬性过滤**~~（已撤销）：AI 随心搭已做 `target_gender` 硬过滤（详见 `docs/AI核心功能设计.md` §3.19）；AI 模特端仍通过模特图池本身的 gender 字段让商家自行选择

## 八、商业模式与成本

### 8.1 成本结构

> **2026-07 实测更新**：原估算"0.1-0.3 元/张"已废弃，以下为接入千问 aitryon-plus 模型族（aitryon-plus VTON + aitryon-refiner 精修 + wan2.7-image 图生图）+ qwen3.5-flash 后的成本拆解。

#### 8.1.1 单次换装成本拆解（用户端·AI 随心搭）

以"用户上传照片 + 上衣+裤子+帽子 3 件搭配"为例（首轮推荐 + 2 轮反馈）：

| 节点 | 模型 | 调用次数 | 单次成本 | 小计 |
|---|---|---|---|---|

## 非功能性需求（安全）

> 2026-08-01 新增小节,基于 AI 随心搭前端代码审查发现的安全缺陷,提炼为后续迭代的强制安全需求。所有新增/变更接口必须满足以下要求,已有接口在对应批次修复中逐步对齐。

### 1. IDOR 防护:AI 随心搭任务归属校验

- **范围**:AI 随心搭所有任务操作接口,包括 `select` / `accept` / `feedback` / `get_result`。
- **要求**:后端必须校验当前请求用户(token 中的 userId)与 `ai_task.user_id` 一致,任一不一致直接返回 403。
- **背景**:任务 taskId 可枚举,若不校验归属,任意登录用户可查询/操作他人搭配结果,导致隐私泄露与 credits 被恶意消耗。
- **实现位置**:Java 侧 outfit Controller / Python 侧 ai-outfit 服务入口校验,前端不参与判定(前端 userId 不可信)。

### 2. WS 鉴权:WebSocket 路径 userId 与 token userId 一致性校验

- **范围**:AI 随心搭 `/ws/ai/{userId}` 与 AI 模特 `/ws/model/{userId}` 两类 WebSocket 端点。
- **要求**:服务端建立连接时必须校验解析出的 `userId` 与路径上的 `userId` 完全匹配,任一不一致直接关闭连接(关闭码 4001)。
- **实现**(F8 已落地,2026-07 前端审查):鉴权顺序为① 网关 `AuthGlobalFilter` 校验 JWT 后透传 `user-info` header,Python 校验其与路径 userId 一致;② 无 header 时降级为首条认证消息 `{"type":"auth","token":"..."}`(URL query 已停用,避免 token 在日志/Referer 泄露)。
- **背景**:原 WS token 通过 URL query 传递,易在日志/Referer 中泄露;若不校验路径 userId,攻击者可凭自己有效 token 订阅他人任务消息。

### 3. XSS 防护:前端渲染用户输入内容必须先转义 HTML

- **范围**:所有使用 `v-html` 渲染的位置(商品名/商品描述/搜索高亮/AI 推荐理由等)。
- **要求**:
  1. 用户/商家可输入的内容(商品名、店铺名、备注、拒绝原因等)在渲染前必须先做 HTML 转义(`&` / `<` / `>` / `"` / `'`);
  2. 仅当确实需要保留特定标签(如搜索高亮的 `<em>`)时,才在转义后再白名单恢复该标签,且白名单仅限 `<em>` / `</em>`,不允许其他标签或属性;
  3. 禁止使用 `v-html` 直接渲染未经转义的接口返回字段;
  4. 服务端返回的 HTML 片段(如搜索高亮)也必须由前端再次校验后才能渲染,不信任后端。
- **背景**:`search.html` 曾直接 `v-html="item.name"` 渲染商品名,商家可在商品名中注入恶意脚本(存储型 XSS),影响所有浏览该商品搜索结果的用户(对应前端审查 F6)。

### 4. 价格精度:前端价格格式化必须正确处理 0/1/2 位小数场景

- **范围**:所有展示价格的页面(首页/搜索页/商品详情/购物车/订单/AI 搭配结果页/充值套餐/credits 换算等)。
- **要求**:
  1. 价格格式化工具函数(如 `util.formatPrice`)必须能正确处理"整数元"、"1 位小数元"、"2 位小数元"三种场景;
  2. 单元测试覆盖 `0` / `5` / `12.5` / `12.05` / `12.50` / `125` 等典型值,确保不出现"12.5 元变 1.25 元"或"12.05 元变 120.5 元"类错误;
  3. 分↔元换算全程使用整数运算(分),仅在最终展示时转换为元,避免浮点精度丢失;
  4. credits 换算(1 元 = 5 credits)同样遵循上述规则,套餐 credits 数量必须为整数。
- **背景**:`util.formatPrice` 1 位小数分支原判断 `index === p.length - 2`,但 `p` 在该分支为空字符串,导致 `12.5` 元被错误格式化为 `1.25` 元(对应前端审查 F5),直接造成前端展示价与实际支付价 10 倍偏差。
