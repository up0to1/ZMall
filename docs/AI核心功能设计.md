# ZMall AI 功能核心设计

本文档介绍 ZMall 平台两大 AI 功能的设计方案：AI 随心搭（用户端）与 AI 模特（商家端）。内容包括功能规则、请求流程、异步任务、WebSocket 推送、消息队列、数据存储与安全设计。

## 一、总体设计

### 1.1 服务划分

AI 功能由两个 Python 服务承载，与现有 Java 微服务协同工作：

| 服务 | 功能 | 特点 |
|------|------|------|
| `ai-outfit` | AI 随心搭（风格驱动 + 用户选定 + 商品驱动） | LangGraph 多步推理，CPU 密集 |
| `ai-models` | AI 模特（链式换装 + 多姿势 + 多换装） | 链式 VTON + LLM 多 Agent 决策，I/O 密集 |
| `shared` | 两个 Python 服务共享的公共模块 | 模型客户端、Qdrant 客户端、Java 调用客户端、外部服务 |

职责边界：
- Java 负责交易与业务数据：商品、购物车、订单、衣橱、credits 账户、尺码表
- Python 负责 AI 推理与向量检索：意图理解、搭配决策、换装生成、模特图生成
- Java 与 Python 通过 RabbitMQ 与 HTTP 协作

### 1.2 AI 功能使用规则

平台采用 credits 积分制统一管理 AI 功能的配额，两个功能共用同一套积分体系。

| 规则 | 说明 |
|------|------|
| 配额单位 | credits（积分），1 元 = 5 credits |
| 适用范围 | AI 模特（商家端）与 AI 随心搭（用户端，含全部模式）均纳入 credits 管理 |
| 首充赠送 | 用户首次使用 AI 随心搭时赠送 50 credits |
| 充值方式 | 从钱包余额兑换，充值套餐见下方表格 |
| 扣费口径 | 仅成功生成才扣 credits，预扣后成功确认或失败回滚 |
| 配额维度 | AI 模特按 shop_id 计费；AI 随心搭按 user_id 计费 |
| 不可提现 | credits 仅用于 AI 功能消费，不可提现回钱包 |

充值套餐（前端 recharge-dialog 展示）：

| 套餐 | 金额 | credits | 说明 |
|------|------|---------|------|
| 1 | 10 元 | 50 | 无加成 |
| 2（推荐） | 20 元 | 110 | 基础 100 + 加成 10 |
| 3 | 50 元 | 300 | 基础 250 + 加成 50 |
| 4 | 100 元 | 650 | 基础 500 + 加成 150 |

#### 1.2.1 credits 消费明细

| 操作 | 类型 | credits | 说明 |
|------|------|---------|------|
| 风格驱动整流程（一阶段直出） | OUTFIT_DIRECT | 17 | 检索决策 + VTON 3 套一次性扣费 |
| 用户选定模式（选定单品直接 VTON） | OUTFIT_VTON | 5 | 1 套 VTON |
| 商品驱动换装生成 | OUTFIT_VTON | 5 | 单商品直接生成 |
| 反馈调整 | OUTFIT_VTON | 5 | 每轮反馈扣 5 credits，同会话最多 3 轮 |
| AI 模特 · 单图模式 | MODEL_GENERATE | 5 | 1 次任务 |
| AI 模特 · 多换装模式 | MODEL_GENERATE | 18 | 固定，覆盖 1-4 套搭配图 |
| AI 模特 · 多姿势模式 | MODEL_GENERATE | 3 + 3×poseCount | poseCount 默认 3 即 12 credits |
| AI 模特 · 重新生成 | MODEL_REGENERATE | 5 | 手动重新生成 = 新请求重新扣费 |

说明：
- 反馈轮无免费首轮机制，每轮独立扣 5 credits
- 保存到衣橱、加购、下单本身不扣 credits（无 LLM/VTON 成本）
- 反馈弹窗取消不扣 credits

#### 1.2.2 credits 失败退还规则

| 场景 | 退还策略 |
|------|---------|
| 检索失败（LLM/Qdrant 异常） | 全额退还 |
| VTON 全部失败 | 全额退还 5×N credits |
| VTON 部分失败 | 不退还，成功的套装仍可加购/下单，失败套装标记生成失败 |
| VTON API 故障（HTTP 5xx） | 全额回滚，提示服务暂时不可用，不降级展示低质量图 |
| VTON API 超时 | 全额回滚，提示生成超时 |
| 用户主动关闭页面 | 不退还（已消耗算力） |

#### 1.2.3 credits 有效期与扣减

| credits 类型 | 有效期 | 来源 |
|-------------|--------|------|
| 赠送 credits | 30 天 | 首充赠送 50 credits |
| 充值 credits | 永久有效 | 钱包兑换 |

扣减规则：
- 优先扣赠送 credits，再扣充值 credits（FIFO 按过期时间）
- 赠送 credits 剩余 ≤ 3 天时，前端顶部提示即将过期
- 过期赠送 credits 由定时任务每日 0:00 清理
- 预扣使用冻结记录（Redis），确认消耗后删除，回滚时加回原池

#### 1.2.4 评分激励奖励

| 行为 | 奖励 | 触发条件 | 上限 |
|------|------|---------|------|
| AI 模特图评分较高 + 发布 | +1 credit | 评分提交且发布成功 | 每商家每日 5 次 |
| 详细填写拒绝原因（≥20 字） | +1 credit | 拒绝原因提交成功 | 每商家每日 3 次 |

奖励发放到赠送 credits 池，同样 30 天有效期。同一 taskId 仅能享受一次奖励。

### 1.3 配额接口

Java user-service 统一提供 credits 账户接口，Python 通过 `JavaClient` 调用：

| 接口 | 说明 |
|------|------|
| `POST /credits/deduct` | 预扣（原子操作，先扣赠送再扣充值） |
| `POST /credits/confirm` | 确认消耗（删除冻结记录，不可回滚） |
| `POST /credits/rollback` | 回滚释放（删除冻结记录 + 加回原池） |
| `GET /credits/balance/{userId}` | 查询余额 |
| `POST /credits/recharge` | 充值（金额 + 订单号 + 套餐 ID） |
| `POST /credits/award` | 发放奖励 |

## 二、AI 随心搭（用户端）

### 2.1 功能定位与三种入口

AI 随心搭为 C 端用户提供三类生成入口，共享照片会话、credits 余额、衣橱与搭配历史。

| 入口 | 触发方式 | credits | 生成路径 |
|------|---------|---------|----------|
| 风格驱动 | 用户填风格/颜色/品类/店铺等结构化表单 | 17（一阶段直出） | `POST /v1/outfit/agent/recommend` |
| 用户选定 | 从衣橱/购物车/订单/商品搜索选单品 | 5 | `POST /v1/outfit/agent/recommend` |
| 商品驱动 | 商品详情页单商品直接生成 | 5 | `POST /v1/outfit/generate` |

风格驱动与用户选定统称风格驱动模式，走 `ai-outfit` 的 LangGraph 工作流；商品驱动走 `ai-outfit` 的商品驱动工作流。三种入口共享 `user_id` 配额池。

### 2.2 两种使用模式

AI 随心搭按照片来源区分两种使用模式：

| 模式 | 照片来源 | 门槛 | 能力 |
|------|---------|------|------|
| 系统模特模式 | 系统模特图池中的男/女模特 | 零门槛，无需登记身体档案 | 浏览体验 + 穿搭灵感，支持多轮反馈、保存衣橱、加购 |
| 自拍照模式 | 用户上传真人照片 | 必须登记身体档案 + 上传照片 | 真实试穿，支持直接下单 + 尺码推荐 |

性别确定优先级：系统模特 > 用户自拍视觉分析 > 身体信息档案，三者任一可用即可触发性别过滤。

### 2.3 风格驱动模式工作流

风格驱动采用一阶段直出：用户在表单页提交需求后，后端一次完成意图理解、检索、搭配决策与 VTON 生成，前端直接展示换装结果。对外统一 stage 为 `vton`，LangGraph 内部节点仅作路由不外传。

流程：

```
用户提交（表单）→ POST /v1/outfit/agent/recommend
  → 分布式锁（按用户串行化，防并发重复扣费）
  → credits 预扣（风格驱动 17 / 用户选定 5）
  → 写入任务状态（PROCESSING）
  → LangGraph 工作流：
      节点1 意图理解（结构化字段 + 备注解析 + 季节 + 性别确定）
      节点2 Qdrant 向量检索（按品类检索，支持指定店铺与跨店补全）
      节点3 搭配决策（Top10 候选 → LLM 选 Top3 + 推荐理由）
      节点3.5 Reflection 自检（颜色协调/风格一致/季节匹配，最多修正 1 次）
      节点4 链式 VTON 生成换装图
      节点5 上传 OSS + 更新任务状态 + WS 推送
  → 通知 Java 确认或回滚 credits
```

#### 2.3.1 意图理解（节点1）

- 结构化字段（风格标签、颜色、品类、店铺、场景描述）直接透传
- 自然语言备注（选填）由 LLM 解析后合并到结构化字段，LLM 不可用时走关键词降级
- 按月份注入季节标签（3-5 春、6-8 夏、9-11 秋、12-2 冬），用户未填风格时注入默认季节风格
- 确定目标性别（系统模特 > 用户自拍分析 > 身体档案）

#### 2.3.2 向量检索（节点2）

- 按用户指定品类串行检索，未指定时默认 [上衣, 下装, 鞋]
- 指定店铺时限定店内检索，店铺缺货时自动跨店补全并打标跨店来源
- 颜色偏好作为 Qdrant payload 精确过滤
- 性别硬过滤：`target_gender IN (用户性别, "unisex")`，中性款男女均可推荐
- 库存软参考：候选商品标记库存状态但不剔除

#### 2.3.3 搭配决策（节点3）

- 按品类笛卡尔积生成候选组合，Top10 候选喂给 LLM
- LLM 结合用户意图、季节、历史轮次与用户偏好，从 Top10 中选出 Top3 并给出每套推荐理由
- 同套搭配内商品去重，避免重复推荐
- LLM 不可用时降级为相似度排序

#### 2.3.4 Reflection 自检（节点3.5）

- 自检维度：颜色协调性、风格一致性、季节匹配
- 不合格的搭配从 Top10 候选池中重新选择（不重新检索 Qdrant）
- 最多修正 1 次，修正后仍不合格保留原结果，不阻塞主流程

### 2.4 商品驱动模式工作流

用户在商品详情页点击 AI 随心搭，针对单商品直接生成换装图：

```
POST /v1/outfit/generate（扣 5 credits）
  → 照片准备（系统模特或上传自拍，POST /v1/outfit/photo 取得会话 Key）
  → 提交前校验身体档案（未登记时引导去衣橱登记）
  → 生成任务（Python 内部异步 + WebSocket 推送）
  → WS 推送 OUTFIT_PRODUCT 结果（主商品锁定、互补商品可换、可加购）
```

### 2.5 结果展示与用户操作

结果页展示 VTON 换装效果图，用户可执行满意或不满意操作。

满意操作：
- 加购整套：先经尺码确认弹窗（批量推荐尺码），再批量写入购物车
- 立即下单：携带搭配上下文跳转订单确认页
- 保存到衣橱：写入衣橱（itemType=4 AI 搭配效果图）

不满意操作：
- 反馈调整：打开反馈弹窗，提交后每轮扣 5 credits，同会话最多 3 轮
- 直接退出：记录搭配记录（不满意标记）

结果页支持刷新与分享：进入时根据 URL 中 taskId 拉取上一次结果，并用 history.replaceState 同步到 URL。

### 2.6 多轮反馈机制

反馈支持两种粒度：

| 反馈类型 | 触发方式 | 处理 |
|---------|---------|------|
| 换某件单品 | 点单品卡片上的换这个按钮 | 仅替换该单品，其他保留 |
| 换一套重新搭 | 点换一套按钮 | 触发新一轮推荐 |
| 整体搭配不协调 | 勾选整体不协调 | 触发换一套 |
| 反馈内容选填 | 可仅勾选结构化字段或留空 | 留空时系统随机换方向 |

结构化反馈字段（前端表单优先于 LLM 解析）：
- `dislikeColors`：不喜欢的颜色，Qdrant must_not 过滤
- `dislikeItemIds`：不喜欢的商品，检索后置过滤
- `wantStyleTags`：想要的风格，合并到风格标签重新检索

dislike 累积规则：
- 仅用户主动勾选单品 + 属性维度时累积
- 整体不协调与换一套不推断 dislike，避免画像噪声
- 累积的 dislike 带衰减：90 天内全权重，90-180 天半权重，180 天以上不生效

### 2.7 我的衣橱与搭配来源

用户可从三个来源挑选单品参与搭配：

| 来源 | 接口 | 说明 |
|------|------|------|
| 我的衣橱 | `GET /wardrobe/list` | 仅 itemType=1（单品商品）参与搭配召回 |
| 购物车 | `GET /carts/my-item-ids` | 购物车商品 ID 列表 |
| 已购订单 | `GET /orders/user/item-ids` | 已签收订单的商品 ID |

选中单品注入工作流后作为必选商品，其他品类由 Qdrant 检索补全，最终搭配为用户选定单品 + 检索结果。

衣橱条目类型：1 单品商品、2 全身照、3 自拍、4 AI 搭配效果图。类型 4 由满意入库流程自动写入，展示原自拍照 + 换装效果图 + 单品列表。

### 2.8 季节感知

- 节点1 根据当前月份注入季节标签与默认风格
- 商品打标 season 字段（spring/summer/autumn/winter/all），基础款标 all 全季可推
- 节点2 检索时过滤 `season IN (当前季节, "all")`

### 2.9 性别与服装搭配

- 商品上架时强制标注 target_gender（男装/女装/中性），默认中性
- 节点2 Qdrant 硬过滤：`target_gender IN (目标性别, "unisex")`
- LLM prompt 双保险：发现跨性别候选时排除该套
- 未登记身体档案时前端禁止提交，引导去衣橱登记
- 系统模特性别与身体档案性别不一致时前端拦截提示

### 2.10 尺码推荐

用户加购/下单时，基于身体信息自动推荐尺码。

数据模型：
- `size_chart_reference` 表：店铺维度尺码对照表，shop_id=0 为系统模板，商家可一键复制到自己店铺后修改
- `user_body_profile` 表：用户身体档案（身高、体重、三围等），支持多档案

查询三级回退：商品专用绑定 > 店铺品类通用表 > 系统模板。

接口（`/items/size-chart/*`）：
- `recommend-by-item`：按商品推荐尺码（AI 随心搭推荐使用）
- `recommend-batch`：批量推荐（多商品场景）
- `shop/**`：商家管理店铺尺码表

### 2.11 个性化推荐画像

基于用户行为信号构建风格画像，注入推荐链路。

信号权重：搭配采纳 3.0、下单 2.0、加购 1.5、浏览 1.0、不喜欢 -2.0、换一套 -1.0。

画像产出：
- `top_styles` / `top_colors`：Top5 偏好风格与颜色
- `price_distribution`：价格分布
- `style_vector`：加权 CLIP 风格向量（1024 维）
- `profile_confidence`：画像置信度（信号数量与多样性的函数）

画像应用：
- 节点1 查询向量融合：`final_vector = text_vector × (1-α) + style_vector × α`，α 由置信度决定，用户当前输入始终占主导
- 节点3 跨会话去重：已购买商品 6 个月硬排除，dislike 商品 30 天硬排除
- 数据表 `user_profile_signal` 记录行为信号，每小时聚合写入 Redis

### 2.12 历史记录策略

搭配记录按三层分级保留：

| 层级 | 存储 | 保留策略 |
|------|------|---------|
| 任务级临时 | Redis 任务状态 + state 快照 | 30 天 |
| 搭配级持久化 | `ai_outfit_record` 表 | 满意永久保留、不满意 90 天、未操作 30 天 |
| 衣橱级收藏 | `user_wardrobe`（itemType=4） | 永久保留 |

- 满意搭配永久保留，供搭配历史回看与复购
- 不满意记录保留 90 天，用于画像负样本训练
- 任务状态实时快照 30 分钟 TTL（任务进行中），完成后由任务级快照接管

### 2.13 用户偏好持久化

- `user_preference` 表持久化显式偏好：不喜欢的颜色、想要的风格、不喜欢的商品、常买价格区间
- 反馈时累积写入，下次进入 AI 随心搭自动加载注入推荐链路
- 我的偏好页面提供查看与重置

### 2.14 商品库同步

平台商品上下架或更新时，通过 MQ 同步到 Qdrant 向量库：

```
商品保存/上下架 → Java 发 MQ（item.upsert / item.delete）
  → ai-outfit 消费 → 更新 Qdrant payload（color/season/stock/target_gender）
```

- 仅穿搭类目商品（上衣/下装/鞋/帽子/包/配饰）入 Qdrant，避免向量库膨胀
- 图片变更时才重新编码向量，仅字段变更走 payload 更新
- 失败重试 3 次后进死信队列，死信消费者再重试 1 次
- 提供全量入库脚本与定时对账脚本，保证 MySQL 与 Qdrant 一致

## 三、AI 模特（商家端）

### 3.1 功能定位

AI 模特为商家提供商品展示图生成能力：商家选择商品与模特图，AI 链式换装生成模特穿着效果图，可评分、发布到商品主图，高质量图入系统池复用。

支持品类：上衣 / 下装 / 全身套装 / 帽子。不支持鞋 / 包 / 配饰（商家端只做服装主体）。

### 3.2 系统模特图池

平台统一的系统模特图池（`system_model_image` 表）：

- 全平台商家共用同一池子，均可查询启用状态的模特图
- 仅创建者可修改/删除自己的模特图
- 商家上传时自动加店铺名水印，防止滥用
- 图片存 OSS（未启用时本地），模特图含性别、肤色、身高、体重、年龄段、体型、风格标签等字段

模特图来源（source 字段）：0 商家上传、1 AI 任务后保存（评分较高入库）、2 平台运营上传、3 AI 自动生成。

### 3.3 三种生成模式

| 模式 | 说明 | 商品数 | 输出 | credits | 典型场景 |
|------|------|--------|------|---------|---------|
| single 单图 | 单套商品链式换装 | 1 上装 + 1 下装 / 1 全身套装 | 1 张最终图 + N 张中间图 | 5 | 单品上新主图 |
| multi_outfit 多换装 | 多套搭配组合 | 2-4 件（可同品类多件） | 每套 1 张图 | 18 | 一次拍多套搭配 |
| multi_pose 多姿势 | 同一套服装多姿势变体 | 与 single 相同 | 1 基准图 + N 姿势变体 | 3 + 3×poseCount | 单款多角度展示 |

组合规则：商家选定商品后，LLM 基于风格/颜色/品类推荐 1-4 套合法搭配组合，LLM 不可用时降级走笛卡尔积。每套组合共用同一张模特基准图，保证同脸一致。

### 3.4 生成流程

AI 模特采用异步任务模式，Java 校验入队、Python 消费生成、结果回流 Java。

```
① 商家选商品（1-4 件，品类校验 + 归属校验）
② POST /items/admin/ai-model/generate
   → Java 校验品类冲突规则 + 配额预扣
   → 生成 taskId → 写 ai_task（PENDING）→ 发 MQ（ai.model.generate）
③ Python ai-models 消费：
   → 按 generationMode 路由到对应工作流
   → 链式 VTON 生成（中间图 + 最终图）
   → 多 Agent 决策评估（可选）
   → 上传 OSS → 发 MQ（ai.model.result）
④ Java 消费：
   → 更新 ai_task（SUCCESS/FAILED）
   → 确认/回滚 credits
   → WebSocket 推送商家前端
```

品类冲突规则：
- 同品类最多 1 件
- 全身套装与上衣/下装互斥
- 全身套装与帽子可共存

链式换装顺序：全身套装优先（一次覆盖全身），再上衣、下装、帽子。全身套装一次 VTON 完成全身换装。

### 3.5 多 Agent 决策

AI 模特可选启用 LLM 多 Agent 决策层，用于提升生成质量。决策层与执行层分离：LLM 负责策划与评估，VTON 只负责换装执行。

5 个角色分工：

| 角色 | 职责 |
|------|------|
| 衣品审美大师（EU/Asia） | 策划阶段输出风格特征描述；评估阶段评 VTON 执行质量 |
| 摄影师 | 策划阶段推荐模特图（商家未指定时）；评估阶段评姿势自然度 |
| 灯光师 | 评估光照，输出中文后处理意图 |
| 化妆师 | 评估妆容，输出中文后处理意图 |
| 导演（主 Agent） | 汇总决策：VTON 顺序优化、合格判定、后处理指令 |

决策权分层：
- 硬决策归商家：商品组合、模特图选择、是否发布
- 软决策归系统：VTON 顺序、模特图推荐、后处理调光调妆
- 信息层：风格特征描述仅展示参考，不阻塞输出

流程：
```
策划阶段（3 子 Agent 并行）→ 链式 VTON 执行 → 评估阶段（5 子 Agent 并行）
  → 合格（综合评分 ≥ 0.8）→ 上传 OSS
  → 可后处理（灯光/妆容不达标）→ 图像精修 → 全 5 角色重评（限 1 轮）
  → 发布由商家主动触发
```

降级策略：
- 策划阶段 LLM 失败：跳过策划，按默认链式顺序直接生成
- 评估阶段 LLM 失败：默认合格输出，综合评分取中位值
- 后处理失败：用 VTON 原图，标记后处理失败日志
- LLM 决策层失败不阻塞主流程，自动降级为无决策模式

### 3.6 评分、发布与拒绝

生成完成后商家可对结果评分、发布、拒绝：

| 操作 | 接口 | 说明 |
|------|------|------|
| 评分 | `POST /items/admin/ai-model/rating` | 五星制 + 可选标签 + 备注；评分较高 + 勾选入池则自动入系统池 |
| 发布 | `POST /items/admin/ai-model/publish` | 选 1 张图发布到对应商品主图；1 图只能发布 1 个商品 |
| 拒绝 | `POST /items/admin/ai-model/reject` | 填写拒绝原因（≤512 字），用于持续优化 |

发布规则：
- 商品可被多次发布，后发布覆盖前发布，旧图保留可回滚
- 中间图也可发布（如穿上衣后的图发布到上衣商品）

评分激励：评分较高 + 入池 + 发布奖励 1 credit（每日 5 次上限）；详细填写拒绝原因奖励 1 credit（每日 3 次上限）。

### 3.7 商家端任务列表

商家在任务列表页查看生成进度与结果：

- WebSocket 实时刷新（收到消息时局部更新对应行）
- 存在进行中任务时启动兜底轮询，任务结束后自动停止
- 结果展示：N 张中间图 + 最终图 + 综合评分 + 风格特征描述
- 支持逐张评分、发布、重新生成

## 四、横向设计

### 4.1 任务状态机

```
PENDING ──→ PROCESSING ──→ SUCCESS
   │            │
   │            ├──→ FAILED
   │            └──→ TIMEOUT（定时任务扫描标记）
   │
   └──→ CANCELLED
```

- PENDING → PROCESSING：Python 开始消费
- PROCESSING → SUCCESS/FAILED：Python 生成完成
- PROCESSING → TIMEOUT：Java 定时任务扫描超时任务，标记超时并回滚 credits
- 任何终态不可逆

### 4.2 超时与补偿

| 场景 | 兜底方案 |
|------|---------|
| Python 生成超时 | Java 定时任务扫描标记 TIMEOUT + 回滚 credits |
| 模型 API 瞬时失败 | 重试 3 次（指数退避），超过标记 FAILED |
| WebSocket 断连 | 前端轮询兜底 |
| MQ 消息丢失 | 消息持久化 + 消费确认 + 定时任务对账 |

### 4.3 WebSocket 推送

```
用户端：ws(s)://{host}/ws/ai/{userId}
商家端：ws(s)://{host}/ws/model/{userId}
```

- 按 userId 建连（用户可能开多个页面），同一用户的所有连接均收到推送
- 鉴权：onopen 后发送首条消息 `{type:"auth", token}`，服务端校验 JWT 后确认
- 客户端 30 秒发送 ping 心跳，服务端回 pong
- 前端未收到推送时用 taskId 轮询兜底

消息类型：

| 类型 | 触发场景 |
|------|----------|
| `OUTFIT_PRODUCT` | 商品驱动结果 |
| `OUTFIT_AGENT` | 风格驱动结果 |
| `OUTFIT_RECOMMEND_RESULT` | 候选推荐结果 |
| `OUTFIT_VTON_RESULT` | VTON 换装结果 |
| `OUTFIT_ACCEPTED` | 用户采纳完成 |
| `OUTFIT_AGENT_FEEDBACK` | 多轮反馈完成 |
| `MODEL` | AI 模特任务状态 |

### 4.4 消息队列

```
Exchange: ai.model.exchange  (AI 模特)
  ├── ai.model.generate  → Python 消费（任务下发）
  └── ai.model.result    → Java 消费（结果回流）

Exchange: ai.outfit.exchange  (AI 随心搭)
  └── ai.outfit.result   → Java 消费（配额确认/回滚）
```

- AI 随心搭生成任务不走 MQ（Python 内部异步 + WS 推送更快），MQ 仅用于通知 Java 确认/回滚 credits
- AI 模特生成任务走 MQ（异步任务模式）
- 商品库同步独立 Exchange（item.sync.exchange），带死信队列

### 4.5 幂等性设计

| 场景 | 幂等方案 |
|------|---------|
| MQ 消息重复消费 | 消费前查 ai_task 状态，已终态则跳过 |
| WebSocket 重复推送 | 前端按 taskId 去重 |
| 配额确认/回滚重复调用 | 删除冻结记录前检查存在性 |
| 前端轮询重复请求 | 幂等查询，无副作用 |

### 4.6 鉴权与安全

#### 4.6.1 接口鉴权

- Gateway JWT 鉴权，透传 user-info（userId + shopId）给下游
- Python 从 user-info header 解析 userId，不信任客户端传入的 userId
- 任务操作（select/accept/feedback/get_result）校验 taskId 归属当前用户，越权返回 403

#### 4.6.2 WebSocket 鉴权

双层防护：
- 网关层：校验 WS 升级请求的 JWT 签名与过期时间，通过后将 userId 写入 header 透传
- Python 兜底层：校验 user-info header 与路径 userId 一致；或等待首条 auth 消息校验 token，均不一致则关闭连接

#### 4.6.3 前端 OSS 直传

- 商家上传图片走 STS 临时凭证（有效期 15 分钟），不暴露 AccessKey
- STS 最小权限：仅能上传到指定目录，只能写不能读
- 前端校验 JPG/PNG ≤ 5MB，后端二次校验

### 4.7 数据存储

| 商品向量 | Qdrant | 穿搭类目商品，payload 含 color/season/stock/target_gender |
